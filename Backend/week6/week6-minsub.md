## [ROLE-001] Java의 특징과 JVM 위에서 동작한다는 것의 의미를 설명해 주세요.

답변: 자바는 객체지향 언어이고, JVM 위에서 실행된다는 특징이 있습니다. Java 코드는 바로 운영체제에서 실행되는 것이 아니라, 먼저 `.class` 바이트코드로 컴파일이 되고, JVM이 이 바이트코드를 실행합니다.

JVM 위에서 동작한다는 것은 자바 바이트코드가 JVM이 설치된 여러 운영체제에서 실행될 수 있다는 의미입니다.

또 자바는 가비지 컬렉션으로 메모리 관리를 자동화하고, 표준 라이브러리와 멀티스레딩, 예외 처리 등을 제공합니다. 백엔드 개발에선 안정적인 런타임, 생태계, 스프링 같은 프레임워크 지원 때문에 많이 사용되는 것으로 알고 있습니다.

## [ROLE-002] JVM의 역할과 Java 코드가 실행되는 과정을 설명해 주세요.

답변: JVM은 자바 바이트코드를 실행하는 가상 머신입니다. 운영체제와 자바 프로그램 사이에서 바이트코드를 해석하거나 JIT 컴파일을 통해 네이티브 코드로 변환해 실행합니다.

자바 코드 실행 흐름은 보통 `자바 소스 코드 -> javac 컴파일 -> .class 바이트코드 -> ClassLoader 로딩 -> ByteCode Verification -> JVM 실행` 순서로 볼 수 있습니다. 실행 중엔 인터프리터와 JIT 컴파일러가 함께 사용될 수 있고, 자주 실행되는 코드를 JIT 컴파일러를 통해서 네이티브 코드로 최적화해서 성능을 높일 수 있습니다.

## [ROLE-003] JVM 메모리 구조인 Method Area, Heap, Stack, PC Register, Native Method Stack에 대해 설명해 주세요.

답변: JVM은 실행 중 필요한 데이터를 여러 런타임 데이터 영역에 나누어 관리합니다.

- 메서드 영역: 클래스 메타데이터, 메서드 정보, static 변수, 런타임 상수 풀 같은 클래스 수준 정보 저장
- 힙: 객체, 배열이 생성되는 공간이고 가비지 컬렉션의 주요 대상
- 스택: 각 스레드마다 생성되고 메서드 호출하마 스택 프레임이 쌓임 -> 스택 프레임에는 지역 변수, 피연산자 스택, 메서드 반환 정보 등을 저장
- PC 레지스터: 각 스레드가 실행 중인 JVM 명령어 주소를 저장
- Native 메서드 스택: 자바가 아닌 C/C++ 같은 네이티브 메서드 실행에 필요한 스택

백엔드 관점에서는 객체가 많이 생성되면 Heap 사용량과 GC에 영향을 주고, 너무 깊은 재귀나 큰 지역 데이터는 스택오버플로우로 이어질 수 있다는 점을 이해하는 것이 중요하다고 생각합니다.

## [ROLE-004] Java에서 Primitive Type과 Reference Type의 차이를 설명해 주세요.

답변: 원시 타입은 `int`, `long`, `double`, `boolean`처럼 실제 값을 저장하는 기본 타입입니다.

참조 타입은 객체, 배열, String처럼 객체의 위치를 참조하는 타입입니다. 변수에는 객체 자체가 아니라, 객체를 가리키는 참조값이 저장됩니다. 실제 객체는 Heap에 저장되고, 참조 변수는 지역 변수라면 스택 프레임에 저장될 수 있습니다.

예를 들어 `int a = 10`은 값 10 자체를 저장하지만, `User user = new User()`는 `User` 객체를 Heap에 만들고, `user` 변수는 그 객체의 참조를 가집니다. 참조 타입은 null을 가질 수 있으므로 NPE에 주의해야 합니다.

## [ROLE-005] Java의 equals()와 ==의 차이를 설명해 주세요.

답변: `==`는 비교 대상이 원시 타입이면 값을 비교하고, 참조 타입이면 두 변수가 같은 객체를 참조하는지 비교합니다.

반면 `equals()`는 객체의 동등성을 비교하기 위한 메서드입니다.

예를 들어 두 String 객체가 서로 다른 객체여도 문자열 내용이 같으면 `equals()`는 true가 될 수 있는데, `==`는 같은 객체를 참조하지 않으면 false가 될 수 있습니다.

백엔드 개발에서 엔티티나 DTO에서 동등성 기준을 명확히 하는 것이 좋다고 알고 있습니다. 특히 HashSet, HashMap의 key로 사용할 객체라면 `equals()`와 `hashCode()`를 함께 일관되게 재정의해야 합니다.

## [ROLE-006] String, StringBuilder, StringBuffer의 차이를 설명해 주세요.

답변: String은 불변 객체입니다. 한 번 생성된 문자열은 변경되는 게 아니라, 문자열을 더하면 새로운 문자열 객체가 생성되는 구조입니다. 그래서 반복문 같은 곳에서 문자열을 계속 더하면 불필요한 객체 생성이 많아질 수 있습니다.

StringBuilder는 가변 문자열을 다루기 위한 클래스입니다. 내부 버퍼를 사용해서 문자열을 변경하므로 반복적인 문자열 조합에 적합합니다.
다만 동기화를 보장하지 않기 때문에 단일 스레드 환경에서 주로 사용합니다.

StringBuffer도 가변 문자열을 다루지만, 주요 메서드가 동기화되어 있어 멀티스레드 환경에서 상대적으로 안전합니다. 대신 동기화 비용이 있어서 단일 스레드에서는 보통 StringBuilder가 더 적합합니다.

정리하면 변경이 거의 없는 문자열을 String, 반복 조합은 StringBuilder, 동기화가 필요한 가변 문자열은 StringBuffer를 고려합니다.

## [ROLE-008] ArrayList와 LinkedList의 차이를 설명하고, 각각 어떤 상황에서 유리한지 설명해 주세요.

## [ROLE-009] HashMap의 동작 원리와 충돌이 발생했을 때 처리 방식에 대해 설명해 주세요.

## [ROLE-010] Java의 Garbage Collection이 무엇이고, 왜 필요한지 설명해 주세요.

답변: 가비지 컬렉터는 더 이상 참조되지 않는 객체를 JVM이 자동으로 찾아 메모리에서 회수하는 기능입니다.

그래서 자바를 쓰면 C/C++처럼 명시적으로 메모리 해제를 하지 않아도 되지만, 객체 생명주기나 메모리 사용 패턴을 이해해야 안정적인 서버를 운영할 수 있습니다.

GC가 필요한 이유는 힙에 계속 객체가 생성되기 때문입니다. 사용이 끝난 객체를 회수하지 않으면, 메모리가 부족해지고, 결국 OutOfMemoryError가 발생할 수 있습니다.

다만 GC는 자동으로 동작하지만 비용이 없는 건 아닙니다. GC가 자주 발생하거나 Stop-The-World 시간이 길어지면 API 응답 지연으로 이어질 수 있습니다. 따라서 백엔드에선 불필요한 객체 생성을 줄이고, GC 로그와 메모리 지표를 통해 문제를 분석할 수 있어야 합니다.

## [ROLE-011] Spring Framework가 무엇이고, Spring을 사용하는 이유를 설명해 주세요.

답변: Spring Framework는 Java 애플리케이션 개발을 위한 프레임워크이고, 핵심은 IoC Container와 DI입니다. Spring이 객체 생성과 의존성 주입을 담당해주기 때문에 개발자는 객체 간 연결을 직접 관리하지 않아도 되고, 결합도를 낮출 수 있습니다.

또한 트랜잭션, AOP, MVC, 데이터 접근, 보안 같은 백엔드 공통 기능을 제공하기 때문에 반복적인 인프라 코드보다 비즈니스 로직에 집중할 수 있습니다. 그래서 Spring은 유지보수성과 확장성이 중요한 Java 백엔드 애플리케이션에서 많이 사용됩니다.

## [ROLE-012] Spring의 IoC와 DI가 무엇인지 설명해 주세요.

답변: IoC는 Inversion of Control의 약자로, 객체 생성과 의존성 연결의 제어권을 개발자 코드가 아닌 Spring Container가 갖는다는 의미입니다.

DI는 Dependency Injection의 약자로, 객체가 필요한 의존성을 직접 생성하지 않고, 외부에서 주입받는 방식입니다. 예를 들어 컨트롤러가 서비스를 `new`로 직접 만들지 않고, 생성자를 통해서 Service Bean을 주입받는 것이 DI입니다.

Ioc가 큰 개념이고, DI는 IoC를 구현하는 방식이라고 생각합니다. 이 구조를 통해서 이제 객체 간의 결합도를 낮추고, 테스트 시에 Mock 객체를 주입하기 쉬워지며, 구현체 교체도 유연해집니다.

## [ROLE-013] @Component, @Controller, @RestController, @Service, @Repository의 역할과 차이를 설명해 주세요.

답변: 컴퓨넌트는 스프링이 해당 클래스를 빈으로 등록할 수 있게 하는 어노테이션이고, 컨트롤러, 서비스, 리포지토리는 모두 컴포넌트의 특수화된 형태입니다.

`@Controller`는 Spring MVC에서 요청을 처리하는 계층을 의미하고, `@RestController`는 `@Controller`와 `@ResponseBody`를 합친 형태로, 메서드 반환 값을 View가 아니라 HTTP Response Body에 JSON 형태로 반환할 때 사용합니다.

`@Service`는 비즈니스 로직을 담당하는 서비스 계층에 사용하고, `@Repository`는 DB 접근 계층에 사용합니다.

그래서 각 계층의 역할을 명확히 표현하고 스프링이 계층별 기능을 적용할 수 있게 한다는 차이가 있다고 알고 있습니다.

## [ROLE-014] @Autowired와 생성자 주입의 차이를 설명하고, 생성자 주입이 권장되는 이유를 설명해 주세요.

답변: `@Autowired`는 스프링 컨테이너에 등록된 빈을 필요한 곳에 주입해달라는 어노테이션으로 알고 있습니다. (필드, 생성자, 세터 등에 사용 가능)

과거에는 필드에 `@Autowired`를 붙이는 방식도 많이 사용했는데, 최근에는 생성자 주입이 더 권장되는 것으로 알고 있습니다. 생성자 주입은 객체가 생성되는 시점에 필요한 의존성을 반드시 주입받도록 강제할 수 있고, `final` 필드를 사용할 수 있어 불변성을 높일 수 있습니다.

또 생성자 주입은 테스트 코드에서 직접 객체를 생성해서 Mock 의존성을 넣기 쉽고, 순환 참조 문제를 더 빨리 발견하는 데도 유리합니다.
스프링에서 생성자가 하나뿐이면 생성자에 `@Autowired`를 생략해도 자동으로 주입됩니다.

## [ROLE-015] Spring Bean이 무엇이고, Bean 생명주기에 대해 설명해 주세요.

답변: 스프링 빈은 스프링 컨테이너가 생성하고 관리하는 객체입니다. 개발자가 `@Component`, `@Service`, `@Repository`, `@Controller`, `@Bean` 등을 통해 등록하면 스프링이 해당 객체의 생성, 의존성 주입, 초기화, 소멸 과정을 관리합니다.

빈 생명주기는 일반적으로 `Bean 정의 읽기 -> 객체 생성 -> 의존성 주입 -> 초기화 콜백 -> 사용 -> 소멸 콜백` 흐름으로 볼 수 있습니다.

초기화 단계에선 `@PostConstruct`, `InitializingBean`, init method 등을 사용할 수 있고, 소멸 단계에서는 `@PreDestroy`, `DisposableBean`, destroy method 등을 사용할 수 있습니다.

백엔드 개발에선 빈이 싱글톤으로 관리되는 경우가 많아서 상태를 필드에 저장할 때 동시성 문제를 조심해야 되는 걸로 알고 있습니다.

## [ROLE-016] Spring MVC 요청 처리 흐름을 DispatcherServlet 중심으로 설명해 주세요.

답변: 스프링 MVC에선 `DispatcherServlet`이 프론트 컨트롤러 역할을 합니다. 클라이언트 요청이 WAS의 Servlet Container로 들어오면, 해당 요청은 먼저 `DispatcherServlet`으로 전달됩니다.

그다음 `DispatcherServlet`은 핸들러매핑을 통해 요청 URI와 HTTP 메서드에 맞는 컨트롤러 메서드를 찾습니다. 핸들러어댑터가 해당 메서드를 실행하고, 컨트롤러는 필요한 요청 값을 받아 서비스를 호출합니다.

## [ROLE-021] Java의 Checked Exception과 Unchecked Exception의 차이를 설명해 주세요.

답변: Checked Exception은 컴파일 시점에 예외 처리를 강제하는 예외입니다. `Exception`을 상속하지만 `RuntimeException`을 상속하지 않는 예외들이 여기에 해당합니다. (ex IOException, SQLException)

Unchecked Exception은 컴파일러가 예외 처리를 강제하지 않는 예외입니다.
(ex) NPE, IllegalArgumentException, IndexOutOfBoundsException)

Checked Exception은 호출자가 반드시 처리하거나 던지도록 강제할 수 있다는 장점이 있지만, 계층을 지날수록 불필요한 throws 선언이 많아질 수 있습니다. Unchecked Exception은 코드가 간결해지지만, 명확한 예외 설계와 전역 예외 처리가 필요합니다.

스프링에서는 데이터 접근 예외를 런타임 예외 계층으로 추상화하는 경우가 많고, API에서는 `@ControllerAdvice`로 비즈니스 예외를 일관된 Error Response로 변환하는 구조를 많이 사용합니다.

## [ROLE-022] Java에서 final 키워드가 변수, 메서드, 클래스에 사용될 때 각각 어떤 의미인지 설명해 주세요.

## [ROLE-031] JPA의 영속성 컨텍스트가 무엇이고, 1차 캐시, 변경 감지, 쓰기 지연에 대해 설명해 주세요.

답변: 영속성 컨텍스트는 Entity를 관리하는 논리적 저장 공간입니다. JPA에서 EntityManager는 영속성 컨텍스트를 통해 엔티티의 상태를 관리합니다.

1차 캐시는 같은 트랜잭션 또는 같은 영속성 컨텍스트 안에서 이미 조회한 엔티티를 다시 조회할 때 DB를 다시 조회하지 않고 메모리에서 반환하는 기능입니다.

변경 감지는 영속 상태의 엔티티 값이 변경되었을 때, 트랜잭션 커밋 시점에 JPA가 변경 내용을 감지해 update SQL을 생성하는 기능입니다. 그래서 영속 상태의 엔티티는 별도 save 호출 없이도 변경이 반영될 수 있습니다.

쓰기 지연은 persist나 변경 작업이 발생할 때 SQL을 즉시 실행하지 않고, 영속성 컨텍스트의 쓰기 지연 SQL 저장소에 모아두었다가 flush 시점에 DB에 반영하는 방식입니다.

## [ROLE-032] JPA에서 Lazy Loading과 Eager Loading의 차이를 설명해 주세요.

답변: Lazy Loading은 연관된 엔티티를 실제로 사용할 때 조회하는 방식입니다. 예를 들어 멤버를 조회할 때 팀을 바로 조회하지 않고, `member.getTeam()`처럼 접근하는 시점에 팀을 조회합니다.

Eager Loading은 엔티티를 조회할 때 연관 엔티티도 함께 조회하는 방식입니다. 필요한 데이터를 한번에 가져올 수 있지만, 예상하지 못한 Join이나 추가 쿼리가 발생할 수 있습니다.

실무에서는 기본적으로 Lazy Loading을 선호하는 경우가 많습니다. 필요한 조회 화면이나 API에 따라 Fetch Join, EntityGraph, DTO Projection 등을 사용해 필요한 데이터만 명시적으로 가져오는 것이 더 예측 가능하기 때문입니다.

## [ROLE-033] JPA N+1 문제가 무엇이고, Fetch Join, EntityGraph, Batch Size로 해결하는 방법을 설명해 주세요.

답변: N + 1 문제는 처음 1번의 쿼리로 N개의 Entity를 조회한 뒤, 각 엔티티의 연관 데이터를 가져오기 위해 N번의 추가 쿼리가 발생하는 문제입니다.

예를 들어서 게시글 100개를 조회한 뒤에 각 게시글의 작성자에 접근하면, 게시글 조회 1번에 작성자 조회 100번이 추가되어 총 101번의 쿼리가 발생할 수 있습니다.

Fetch Join은 JPQL에서 연관 Entity를 함께 조인해서 한 번에 가져오는 방식입니다.
EntityGraph는 어떤 연관관계를 함꼐 로딩할지 선언적으로 지정하는 방식입니다. Batch Size는 연관 엔티티를 하나씩 가져오지 않고, 여러 개의 식별자를 묶어서 한 번에 조회하도록 하는 방식입ㅇ니다.

다만 Fetch Join은 컬렉션 페이징에서 데이터 중복이나 메모리 페이징 문제가 발생할 수 있으므로, 조회 목적에 따라 Fetch Join, Batch Size, DTO Projection을 적절히 선택해야 합니다.
