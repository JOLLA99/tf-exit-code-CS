## [ROLE-001] 클라우드 컴퓨팅이 무엇이고, 온프레미스 환경과 어떤 차이가 있는지 설명해 주세요.

답변:

- 클라우드 컴퓨팅은 인터넷을 통해 서버, 스토리지, 네트워크 등의 IT 자원을 필요한 만큼 빌려서 사용하는 방식입니다. 직접 서버를 구매하고 사내에 설치하는 대신 클라우드 서비스를 제공하는 곳에서 인프라를 사용합니다. 편리한 대신에 특정 클라우드 서비스에 강하게 의존하면 다른 환경으로 이전하기 어려울 수 있습니다.
- 온프레미스 환경은 기업이 직접 서버 및 네트워크 장비를 구매하여 인프라를 직접 소유하지만 초기 비용도 높고 구축하는 데 시간이 굉장히 오래 걸립니다. 또한 유지보수도 회사 내에서 직접 관리해줘야 합니다.

## [ROLE-002] IaaS, PaaS, SaaS의 차이를 설명해 주세요.

답변:

- **IaaS(Infrastructure as a Service)**
    - IaaS는 서버, 스토리지, 네트워크 같은 인프라를 제공하는 서비스입니다. 사용자는 제공받은 인프라 위에 애플리케이션 등을 올려 관리합니다. 원하는 환경을 직접 구성 가능하지만 관리 비용과 운영 복잡도가 높습니다.
- **PaaS(Platform as a Service)**
    - 애플리케이션을 개발하고 실행할 수 있는 플랫폼을 제공하는 서비스입니다. 사용자는 서버나 OS를 직접 관리할 필요없이 애플리케이션 개발에만 집중하면 됩니다. 관리 부담은 감소되지만 자유도가 낮고 플랫폼 의존성이 커지기 쉽습니다.
- **SaaS(Software as a Service)**
    - 완성된 소프트웨어를 인터넷을 통해 서비스 형태로 제공하는 것입니다. 사용자는 단순히 서비스를 사용합니다. (ex: Gmail, Notion, Slack) 바로 사용할 수 있고 관리라는 게 없지만 커스터마이징에 제한이 있고 서비스 제공자에 대한 의존이 굉장히 큽니다.

## [ROLE-003] Public Cloud, Private Cloud, Hybrid Cloud의 차이를 설명해 주세요.

답변:

- **Public Cloud**
    - 클라우드 서비스 제공업체가 구축한 인프라를 여러 고객이 함께 사용하는 방식입니다. 초기 구축 비용이 적고 빠르게 사용 가능하지만 클라우드 사업자에 대한 의존성이 존재하고 원하는 수준으로 인프라를 세밀하게 제어하기 어려울 수 있습니다.
- **Private Cloud**
    - 특정 기업이나 조직만 사용 가능한 전용 클라우드 환경입니다. 기업이 자체 서버에 OpenStack이나 Kubernetes 등을 구축하여 내부 서비스를 운영하는 경우입니다.
    - 높은 수준의 제어와 커스터마이징이 가능하지만 초기 구축 비용이 크고 직접 관리해야 하는 부분이 많습니다.
- **Hybrid Cloud**
    - Public Cloud와 Private Cloud를 함께 사용하는 방식입니다.
    - 민감한 데이터나 내부 시스템은 프라이빗 쪽으로 돌리고 트래픽을 처리하는 일반 서비스들은 퍼블릭에 둘 수 있습니다.
    - 평상시에는 프라이빗을 사용하다가 트래픽이 급증하면 퍼블릭을 추가로 사용하는 Cloud Bursting 방식도 가능합니다.

## [ROLE-004] 클라우드에서 Region과 Availability Zone이 무엇인지 설명해 주세요.

답변:

- **Region**
    - Region은 클라우드 사업자가 특정 지리적 위치에 구축한 독립적인 클라우드 인프라 영역입니다. 예를 들어 서울, 도쿄, 미국 리젼, 서울 내에서도 판교 리전과 같이 나눠질 수도 있습니다.
    - 서비스를 배포할 리젼을 선택할 때에는 사용자와의 네트워크 거리, 지연 시간과 같은 점을 고려해 한국 사용자를 대상으로 하는 서비스라면 일반적으로 서울 리젼을 고려할 수 있습니다.
- **Availability Zone**
    - AZ란 하나의 리젼 안에서 물리적으로 분리된 데이터센터 또는 그 그룹입니다.
    - AZ는 전력, 네트워크 등의 인프라를 독립적으로 구성하여 한 AZ에서 장애가 발생하더라도 다른 AZ에서 서비스를 계속 운영할 수 있도록 설계됩니다.

⇒ 굳이 리젼과 AZ를 나누는 이유는 장애를 격리하고 가용성을 높이기 위해서입니다. 서버를 하나의 AZ에만 배치하면 AZ에 장애가 났을 때, 서비스가 중단됩니다. 또한 리젼 간에도 분산이 가능합니다.

## [ROLE-005] VPC가 무엇이고, 클라우드 네트워크에서 어떤 역할을 하는지 설명해 주세요.

답변:

- **VPC(Virtual Private Cloud)**
    - VPC란 클라우드 안에서 내가 사용할 수 있도록 논리적으로 격리된 가상 네트워크입니다.
    - 예를 들어 VPC 하나를 만들고 IP 주소 대역을 정한 뒤, 그 안에 여러 서브넷을 구성할 수 있습니다.
        
        ```
        VPC
        10.0.0.0/16
        │
        ├── Public Subnet
        │   └── Web Server (10.0.1.0/24)
        │
        └── Private Subnet
            └── DB Server (10.0.2.0/24)
        ```
        
    - VPC는 클라우드 리소스의 네트워크를 격리하고 통제하는 역할을 합니다. VPC 안에서 IP 주소 대역, 서브넷, 라우팅, NAT Gateway 등 네트워크 구성을 직접 관리할 수 있습니다.
    - 이를 통해 클라우드에서 내 서버들이 어떤 네트워크에 있고 어떻게 서로 통신할 것인지를 정의합니다.

## [ROLE-006] Public Subnet과 Private Subnet의 차이를 설명해 주세요.

답변:

- VPC 안의 네트워크를 더 작은 네트워크로 나눈 것이 서브넷입니다. 일반적으로 인터넷에서 접근해야 하는 리소스들이 퍼블릭, 외부 인터넷에서 직접 접근할 필요가 없는 리소스를 프라이빗에 둡니다.
- 퍼블릭 서브넷은 인터넷 게이트웨이를 통해 인터넷과 직접 통신할 수 있습니다. 프라이빗 서브넷은 외부 인터넷에서는 들어올 수 없지만, 프라이빗 서브넷에서 외부 인터넷으로 나가려면 NAT Gateway를 통해 외부로 나갈 수 있습니다.
    
    ```
    Public Subnet
          ↓
    Internet Gateway
          ↓
    Internet
    ```
    
    ```
    Private Subnet
          ↓
    NAT Gateway
          ↓
    Internet Gateway
          ↓
    Internet
    ```

## [ROLE-007] Security Group과 Network ACL의 차이를 설명해 주세요.

답변: 

- **Security Group**
    - Security Group은 EC2 같은 리소스의 네트워크 인터페이스(ENI)에 적용되는 가상 방화벽입니다.
    - 즉, 특정 서버에 어떤 트래픽을 허용할지 설정합니다.
    - Allow 규칙만 설정이 가능하고 기본적으로 Stateful합니다. 또한 시큐리티 그룹을 여러개 만들어 서버마다 적용시킬 수 있습니다.
        
        ```
        Client
          │
          │ 요청
          ↓
        Server
          │
          │ 응답
          ↓
        Client
        ```
        
- **Network ACL**
    - 서브넷 단위로 적용되는 네트워크 접근 제어 목록입니다.
    - Allow와 Deny를 모두 설정 가능하고 Stateless합니다. 규칙에 우선순위 번호도 존재합니다.
- *Stateless > 각 방향의 트래픽을 독립적으로 판단*
    - *Client > Server를 허용했더라도 반대 규칙도 필요함*

## [ROLE-008] NAT Gateway가 무엇이고, 어떤 상황에서 사용하는지 설명해 주세요.

답변:

- **NAT Gateway**
    - 프라이빗 서브넷의 리소스가 인터넷으로 요청을 보낼 수 있도록 해주는 네트워크 서비스입니다.
    - 보통 프라이빗 서브넷 내에 애플리케이션 서버가 있다면 공인 IP를 주지 않습니다. 다만 앱 서버가 패키지를 다운로드하거나 도커 이미지를 다운해야 하는 일이 발생할 수 있습니다. 그렇기 때문에 인터넷으로 나가는 통신이 필요해집니다.
    - 인터넷으로 나갈 수 있어야하기 때문에 NAT Gateway는 일반적으로 퍼블릭 서브넷에 배치됩니다.

```
NAT는 Network Address Translation입니다. 프라이빗 서브넷에서 사설 
IP로 외부 서버에 요청을 하면 NAT Gateway가 외부에서 사용할 수 있는 주소로
변환해서 요청을 보냅니다. 
-> 외부에서는 NAT Gateway 공인 IP에서 요청이 온것처럼 보인다 !
```

## [ROLE-009] Load Balancer가 무엇이고, L4 Load Balancer와 L7 Load Balancer의 차이를 설명해 주세요.

답변:

- **Load Balancer**
    - 로드밸런서는 클라이언트의 요청을 여러 서버로 분산하여 특정 서버에 트래픽이 집중되는 것을 방지하는 장치입니다.
    - 서버가 하나 뿐이라면 트래픽이 많아졌을 때 이를 감당하기 어렵습니다. 그래서 서버를 여러대 두고 그앞에 로드밸런서를 설치하여 요청을 분산시킵니다.
- **L4 LB**
    - L4는 OSI 4계층인 전송 레이어에서 동작합니다.
    - TCP, UCP 이 정보를 기준으로 트래픽을 분산합니다. 그래서 L4는 HTTP의 내용을 직접 이해하지 않습니다.
        
        ```
        GET /users
        POST /orders
        ```
        
        ```
        Source IP
        Destination IP
        Source Port
        Destination Port
        TCP / UDP 같은 정보를 기반으로 처리
        ```
        
    - 장점은 처리 속도가 빠르고 단순합니다. 대신 HTTP 요청 내용을 기반으로 한 세밀한 라우팅이 어렵습니다.
- **L7 LB**
    - L7은 OSI 계층 7계층인 applicaiton layer에서 동작합니다.
    - 대표적으로 HTTP/HTTPS를 이해하고 요청 내용을 기반으로 트래픽을 분산할 수 있습니다. 또한 URL/Host 기반 라우팅이 가능합니다.
    - 대신 L4보다 처리 과정이 복잡합니다.

<aside>
⏰

*왜 쿠버네티스 서비스는 L4일까?*

---

- **서비스는 기본적으로 IP + Port 기준으로 파드를 찾아서 트래픽 전달**
- 그래서 L4 수준의 로드밸런싱을 만듬
- Ingress나 Gateway들이 로드밸런서 다음에서 HTTP 요청 내용을 보고 라우팅을 해줌
- 쿠버네티스의 type: LoadBalancer 이거 자체가 L4 로드밸런서를 연결한다고 함
</aside>

## [ROLE-010] Auto Scaling이 무엇이고, 어떤 기준으로 확장 또는 축소할 수 있는지 설명해 주세요.

답변:

- Auto Scaling
    - 서비스 부하에 따라 서버나 애플리케이션의 실행 개수를 자동으로 늘리거나 줄이는 기능

## [ROLE-011] IAM이 무엇이고, 최소 권한 원칙이 중요한 이유를 설명해 주세요.

답변:

- IAM (Identity and Access Management)
    - IAM은 사용자나 서비스 같은 주체의 인증과 권한 부여를 관리하는 기능입니다. 즉, 누구인지 확인하고 그 사람이 무엇을 할 수 있는지 결정하는 것입니다.
    - IAM에서는 User, Group, Role, Policy 등을 통해 접근 권한을 관리할 수 있습니다.
    - 최소 권한 원칙은 각 사용자나 서비스에 업무 수행에 필요한 최소한의 권한만 부여하는 원칙입니다. 이를 적용하면 계정이나 자격 증명이 탈취되거나 실수로 잘못된 작업을 수행하더라도 접근 가능한 리소스가 제한되기 때문에 보안 사고의 피해 범위를 최소화 할 수 있습니다.

## [ROLE-012] Object Storage와 Block Storage의 차이를 설명해 주세요.

답변:

- **Object Storage**
    - 오브젝트 스토리지는 파일을 오브젝트(객체) 단위로 저장하는 방식입니다. 각 파일이 하나의 오브젝트가 되고 오브젝트에는 데이터, 메타데이터 등이 함께 저장됩니다.
    - 오브젝트 스토리지는 API/HTTP를 통해 오브젝트를 가져오거나 저장하는 방식입니다.
    - 주로 이미지나 동영상, 백업, 로그와 같은 대용량 데이터를 저장하는 데 적합합니다.
- **Block Storage**
    - 저장 공간을 고정된 크기의 블록으로 나누어 디스크처럼 제공하는 방식입니다. 서버에서는 디스크처럼 인식해 파일 시스템을 구성할 수 있어 데이터베이스처럼 낮은 수준의 디스크 I/O가 필요한 서비스에 적합합니다.

## [ROLE-013] 클라우드 환경에서 RDS와 같은 Managed Database를 사용하는 장단점을 설명해 주세요.

답변:

- Managed Database는 DB의 설치, 운영, 백업, 장애 대응 등의 인프라 관리를 클라우드 사업자가 대신 해주는 서비스입니다.
- 이를 사용하면 설치나 백업, 패치와 같은 운영 작업을 직접 관리하지 않아도 되어 운영 부담이 감소합니다. 또한 자동 백업이나 복구 기능을 제공하는 경우가 많아 편리합니다. 그리고 Multi-AZ처럼 고가용성 구성을 제공하는 경우도 존재해 쉽게 진행할 수 있습니다.
- 단점은 우선 비용입니다. 직접 서버에 디비를 설치하는 것보다 비용이 높을 수 있습니다. 또한 managed 서비스이기 때문에 OS나 내부 환경 직접 제어할 수 없을 확률이 높습니다. 그리고 클라우드 사업자에 의존하게 되어 추후에 다른 클라우드 이전이 어려워질 수 있습니다.

## [ROLE-014] CDN이 무엇이고, 정적 리소스 제공에 어떤 장점이 있는지 설명해 주세요.

답변:

- **CDN(Content Delivery Network)**
    - 일반적으로 사용자가 웹 서버에 요청할때 사용자와 서버가 멀리 떨어져있다면 네트워크 지연이 발생할 수 있습니다.
    - CDN을 사용하면 여러 지역에 엣지 서버를 두고 콘텐츠를 사용자와 가까운 곳에서 제공합니다.
    - 사용자가 리소스를 요청했을 때 처음 요청하면 origin server에서 파일을 가져오고 이를 CDN edge에 캐시할 수 있습니다. 재요청시 오리진 서버까지 다녀오지 않아도 된다는 것입니다.
    - 그렇기 때문에 응답 속도가 향상되고 오리진 서버의 부하가 감소합니다. 또한 트래픽 분산도 되고 글로벌 서비스에 유리하기도 합니다.
    - CDN은 그렇기 때문에 특히 변경이 적고 여러 사용자에게 공통으로 제공되는 데이터에 적합합니다.

- **Docker**

    - 따라서 컨테이너는 VM에 비해 일반적으로 시작 속도가 빠르고 리소스 사용량이 적다는 장점이 있습니다.

## [ROLE-017] Kubernetes가 무엇이고, 컨테이너 오케스트레이션이 필요한 이유를 설명해 주세요.

답변:

- Kubernetes
    - 컨테이너화된 애플리케이션을 자동으로 배포하고 운영하기 위한 오픈소스 컨테이너 오케스트레이션 플랫폼입니다. 관리해야 하는 컨테이너의 양이 늘어날 수록 사람이 직접 관리하기는 어려워집니다.

## [ROLE-018] Kubernetes의 Pod, Deployment, Service의 역할을 설명해 주세요.

## [ROLE-020] 무중단 배포가 무엇이고, Blue-Green 배포와 Rolling 배포의 차이를 설명해 주세요.

답변:

- **무중단 배포**
    - 새로운 버전을 배포하는 동안 서비스 중단을 최소화/방지하는 것입니다. 기존 배포되었던 파드가 내려가고 새 파드가 배포되는 과정에서 서비스는 중단될 수 있습니다. 이걸 피하기 위해서 다음의 배포 방식을 사용합니다.
- Blue-Green 배포
    - Blue와 Green이라는 두개의 동일한 환경을 만들어서 배포하는 방식입니다.
    - 운영 중인 환경인 blue이고 새로운 버전은 green에 배포합니다. green에서 충분히 테스트를 한 다음에 트래픽을 한 번에 green으로 전환합니다.
    - blue는 잠시 유지해두고 문제가 발생하면 다시 blue로 트래픽을 돌릴 수 있습니다. 새 버전을 미리 검증 가능하고 빠르게 이전 버전으로 전환이 가능합니다. 다만 두 환경을 동시에 유지해야 해서 리소스 비용이 큽니다.
- Rolling 배포
    - 기존 서버를 조금씩 새 버전으로 교체하는 방식입니다.
    - 예를 들어 파드가 4개가 있고 현재 전부 v1이라면 하나씩 v2로 교체합니다. 일부씩 교체하기 때문에 서비스 중단을 줄일 수 있습니다.
